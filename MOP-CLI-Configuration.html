Colour Key — New Fields
id / runIf — cross-phase linking keys. id: marks a referenceable element; runIf: gates execution on a prior outcome.
onFailure / failureCode — failure escalation. onFailure: controls flow; failureCode: emitted to external systems only.
saveOutputAs / compare_output — output capture & comparison. Saves CLI stdout for later before/after diffing.
Hierarchy change from old format:
✦ Block → steps list (new layer)
✦ Step → commands list (rich objects)
✦ targetNode → target on step
✦ method on block → now on each command
✦ Plain string commands replaced by rich command objects
Part 2 — Section Descriptions
§ 1preNodeHealthCheck
YAML keypreNodeHealthCheck
RunsFirst — before backup or any file change
targetMRF_NODE
Confirms the node service is running and disk space is sufficient before proceeding. Uses id: on commands so execution blocks can reference their outcomes via runIf:. Failure of a critical command uses onFailure: abort_mop.
id: precheck_disk_space cmd: "df -h ${MRF_DESTINATION_PATH}" onFailure: skip_block failureCode: "DISK_FULL" id: precheck_file_exists cmd: "ls ${MRF_DESTINATION_PATH}/${INPUT_FILE}" onFailure: continue
CLIRequired
§ 2backup
YAML keybackup
RunsAfter pre-health check, before activity
targetMRF_NODE
Creates a versioned copy of the current announcement directory. The backup command carries an id: so the rollback execution step can guard the restore with runIf: "backup_copy_cmd.passed".
id: backup_copy_cmd cmd: "cp -rp ${MRF_DESTINATION_PATH}/* /tmp/${VERSION}/" onFailure: skip_block # id used later: runIf: "backup_copy_cmd.passed"
CLIRequired
§ 3aactivity › precheck
YAML keyactivity.precheck
RunsBefore execution blocks
targetsLOCAL · REPO_SERVER · MRF_NODE
Downloads files via REST API or git, stages them on the repo server, and captures a directory snapshot using saveOutputAs:. The snapshot is compared in postcheck to confirm the activity produced changes.
id: precheck_listing cmd: "ls -ltrh ${MRF_DESTINATION_PATH}" saveOutputAs: "pre_dir_listing" validation: type: info_only
CLIOptional
§ 3bactivity › execution  — Core Activity
YAML keyactivity.execution
RunsBetween precheck and postcheck — the actual file transfer and loading
targetsMRF_NODE
Guarded by runIf: "precheck_disk_space.passed" at block level. The SCP step is additionally gated by runIf: "precheck_file_exists.failed" so it is skipped when the file is already present. A conditional if/then/else command selects the correct load command based on ${VERSION}.
TRANSFER_ANNOUNCEMENT_FILES block
runIf: "precheck_disk_space.passed" steps: - id: scp_step target: MRF_NODE runIf: "precheck_file_exists.failed" failureCode: "SCP_TRANSFER_ERROR"
LOAD_ANNOUNCEMENT_FILES block
commands: - if: "${VERSION} == 13.X.X.X" then: - cmd: "cp -r /tmp/..." - cmd: "chmod 777 ..." else: - cmd: "tar -xf /tmp/..."
CLIRequired
§ 3cactivity › postcheck
YAML keyactivity.postcheck
RunsAfter all execution blocks
targetMRF_NODE
Verifies the file loaded with correct permissions using a regex validation, then confirms the directory actually changed by comparing against the precheck snapshot with type: compare_output and comparator: not_equals.
validation: type: regex expression: "-rwxrwxrwx.*${INPUT_FILE}" validation: type: compare_output expression: "pre_dir_listing" comparator: not_equals
CLIOptional
§ 4postNodeHealthCheck
YAML keypostNodeHealthCheck
RunsAfter all activity blocks
targetMRF_NODE
Repeats the SWMS service check to confirm no degradation after file loading. Uses onFailure: abort_mop and failureCode: "SWMS_SERVICE_DOWN_POST_LOAD" for immediate escalation if the service went down during the activity.
cmd: "service swms status" onFailure: abort_mop failureCode: "SWMS_SERVICE_DOWN_POST_LOAD" validation: type: contains expression: "active (running)"
CLIRequired
§ 5arollback › precheck
YAML keyrollback.precheck
RunsFirst step of rollback sequence
targetMRF_NODE
Confirms the backup directory created in §2 still exists before attempting restore. The id: rollback_backup_check on this command is referenced in the rollback execution step as a guard condition.
id: rollback_backup_check cmd: "ls -lrth /tmp/${VERSION}" onFailure: continue validation: type: not_contains expression: "No such file or directory"
CLIRequired
§ 5brollback › execution
YAML keyrollback.execution
RunsCore rollback — restores previous state
targetMRF_NODE
Restore is guarded by a compound runIf requiring BOTH backup commands to have passed. If either failed the restore is skipped but cleanup of the temporary file still runs unconditionally.
runIf: "backup_copy_cmd.passed AND rollback_backup_check.passed" onFailure: continue # always runs — no runIf cmd: "rm -f /tmp/${INPUT_FILE}"
CLIRequired
§ 5crollback › postcheck
YAML keyrollback.postcheck
RunsFinal step of rollback
targetMRF_NODE
Confirms the announcement directory is accessible and intact after rollback. A not_contains check on "No such file or directory" verifies the directory survived the restore.
cmd: "ls -lrth ${MRF_DESTINATION_PATH}" validation: type: not_contains expression: "No such file or directory" successMessage: "Directory accessible — rollback complete"
CLIRequired
Part 3 — Command-Level Fields
id + methodIdentity & Protocol
idOptional. String identifier for cross-phase referencing.
methodCLI or REST — required on every command object.
Assigning id: to a block, step, or command makes it referenceable by any later element via runIf:. IDs must be unique within the template. The method field selects the execution engine — CLI runs a shell command, REST sends an HTTP request.
id: precheck_disk_space method: CLI cmd: "df -h ${MRF_DESTINATION_PATH}" id: get_node_status method: REST
OptionalCommand level
onFailureFailure Escalation
Defaultskip_block
ScopeCommand level only (not step level)
Controls what happens when a command's validation fails:
continue Log the failure and proceed to the next command.
skip_step Skip remaining commands in the current step.
skip_block (default) Skip remaining steps in the current block.
abort_section Abort the entire section (e.g. all of activity).
abort_mop Halt execution of the entire MOP immediately.
OptionalCommand level
failureCodeExternal System Integration
TypeString — arbitrary code token
VisibilityEmitted to external systems only — NOT shown in MOP report
When a command fails and a failureCode is set, the executor emits that code to external monitoring or ticketing systems (e.g. SWMS, ITSM). This allows automated downstream triage without cluttering the human-readable MOP report.
failureCode: "SWMS_SERVICE_DOWN" failureCode: "DISK_FULL" failureCode: "SCP_TRANSFER_ERROR"
OptionalCommand level
runIfCross-Phase Linking
Syntax<id>.<state> — e.g. precheck_disk_space.passed
ScopeBlock, step, or command level
Gate execution on the outcome of any previously identified element. Replaces the removed skipIf — use runIf: "X.failed" to achieve "skip if X passed".
Outcome States
StateMeaning
passedValidation succeeded
failedValidation failed or command errored
skippedElement was skipped by a runIf condition
executedCommand ran regardless of pass/fail
not_executedElement was never reached
Compound Expressions
runIf: "A.passed AND B.passed" runIf: "A.failed OR B.skipped" runIf: "backup_copy_cmd.passed AND rollback_backup_check.passed" # "skip if X passed" idiom: runIf: "precheck_file_exists.failed"
OptionalBlock / Step / Cmd
continueOnFailureStep-Level Default
TypeBoolean — true or false
Defaultfalse
ScopeStep level ONLY — not available at command level
Sets the default failure behaviour for all commands within that step. When true, it is equivalent to setting onFailure: continue on every command. Individual commands can still override with an explicit onFailure: value — the command-level setting always takes precedence.
steps: - id: node_health_step target: MRF_NODE continueOnFailure: false # step default commands: - method: CLI cmd: "service swms status" onFailure: abort_mop # overrides step default
OptionalStep level only
saveOutputAsOutput Capture
TypeString — name of the capture slot
CapturesCLI stdout or REST response body
ScopeCommand level; available to any later command in any section
Saves the full output of the command to a named slot. Any subsequent command — even in a later section — can reference the captured value using validation type compare_output. Typical pattern: capture a directory listing in precheck, compare in postcheck to confirm the activity produced changes.
# In activity.precheck: - id: precheck_listing method: CLI cmd: "ls -ltrh ${MRF_DESTINATION_PATH}" saveOutputAs: "pre_dir_listing" validation: type: info_only
OptionalCommand level
compare_outputOutput Comparison Validation
validation.typecompare_output
expressionName of the saved capture slot (from saveOutputAs)
comparatorequals · not_equals · contains · not_contains · regex
Compares the current command output against a previously saved capture. The comparator field is required when type: compare_output is used. Typical before/after pattern: capture in precheck with saveOutputAs, compare in postcheck with compare_output + not_equals to confirm the directory actually changed.
# In activity.postcheck: validation: enabled: true type: compare_output expression: "pre_dir_listing" # refers to saveOutputAs name comparator: not_equals successMessage: "Directory changed" failureMessage: "Directory unchanged"
Validation typeCLI + REST
Part 4 — Validation Reference
validation:Validation Object Fields
FieldTypeDescription
enabled boolean When false the whole validation block is ignored and the command always passes. Default: true.
type enum Validation algorithm to apply. See CLI and REST type tables below.
expression string The value used by the validation type — a substring, regex pattern, exit code, JSONPath, XPath, or capture name depending on type.
comparator enum Required only when type: compare_output. Values: equals · not_equals · contains · not_contains · regex.
negate boolean When true, inverts the result of the validation. Pass becomes fail and vice versa. Default: false.
criteria string Human-readable description of the acceptance criterion shown in the MOP report.
successMessage string Message recorded in the execution report when validation passes.
failureMessage string Message recorded in the execution report when validation fails.
CLICLI Validation Types
TypeExpression formatDescription
contains substring Passes if stdout contains the given string.
not_contains substring Passes if stdout does NOT contain the string.
regex regex pattern Passes if stdout matches the regular expression.
exit_code "0" or code string Passes if the shell exit code equals the expression value.
compare_output capture name Compares stdout against a previously saved capture. Requires comparator.
info_only (none) Always passes. Command output is recorded as informational only — no pass/fail assessment.
RESTREST Validation Types
TypeExpression formatDescription
http_status "200" / "201" etc. Passes if the HTTP response status code exactly matches.
http_status_range "200-299" Passes if the status code falls within the inclusive range.
json_path JSONPath expression Evaluates a JSONPath against the response body; passes if the result is truthy.
xml_xpath XPath expression Evaluates an XPath against the XML response body; passes if the result is non-empty.
contains substring Passes if the response body contains the given string.
not_contains substring Passes if the response body does NOT contain the string.
regex regex pattern Passes if the response body matches the regular expression.
compare_output capture name Compares response body against a previously saved capture. Requires comparator.
info_only (none) Always passes. Response recorded as informational only.
Part 5 — Step-Level Fields
steps: - ...Step Object Fields
FieldType / ValuesDescription
target machine alias required Identifies the machine that will execute the step's commands. Well-known aliases: LOCAL (executor host), REPO_SERVER (file server), MRF_NODE, or a dynamic variable like ${NEID}. Resolved from constants or the runtime inventory.
id string optional Assigns a cross-phase reference identifier to this step. Later elements can use runIf: "step_id.state" to gate on the step's outcome. Step outcome reflects the worst command outcome within it.
description string optional Human-readable label for this step shown in the MOP report and execution log.
runIf expression optional Gate condition using <id>.<state> syntax. If the condition is false the entire step is skipped (all commands are marked skipped). Supports AND / OR compound expressions.
continueOnFailure boolean optional Default failure behaviour for all commands in this step. When true, equivalent to onFailure: continue on each command. Individual commands override with explicit onFailure:. Only valid at step level — not available on command objects.
Step level Most fields optional CLI + REST
