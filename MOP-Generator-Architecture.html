Part 2 — Section Descriptions
§ 1 preNodeHealthCheck
YAML keypreNodeHealthCheck
TypeList of activity blocks
PositionFirst block in MOP — before any changes
Used byAll node types (SBC, MRF, DPA)
Verifies the node is healthy and stable before any configuration change begins. Failures here must block the activity entirely. Results serve as a baseline for comparison with the post-health check.
cm_adm -a health sbc_health --test all alarm_check --action health virsh list --all
Static CLIRequired
§ 2 backup
YAML keybackup
TypeList of activity blocks
PositionAfter pre-health, before activity
Used byAll node types
Creates a point-in-time backup of the current node configuration or relevant files. This backup is the safety net used during rollback if the activity needs to be undone.
# SBC: full NETCONF XML backup netconfprov --readall > /storage/backup.xml # MRF: announcement directory backup cp -rp $ANN_DIR ${ANN_DIR}.bkp_$(date) # DPA: phones.dat backup cp -p phones.dat OldDLUBKP/phones.dat_bkp$VER
Static CLIRequired
§ 3a activity › precheck
YAML keyactivity.precheck
TypeList of activity blocks
PositionJust before configuration blocks
Used byAll node types
Captures a detailed baseline snapshot of the specific resources being changed — alarm state, table summaries, current versions. Output is compared with the postcheck to confirm the change had the expected effect.
show status show alarms active show crf target-list summary show ibcf virtual-network summary
Static CLIOptional
§ 3b-A activity › configuration
YAML keyactivity.configuration
TypeTable name list → auto-generated
PositionCore activity — one block per table × action
Used bySBC (CIQ-driven XML)
Reads CIQ JSON rows and auto-generates one NETCONF XML block per table per action (CREATE / MODIFY / DELETE). The XML payload is built from tables.<Name>.xmlTemplates or the programmatic fallback builder. Each block stages the XML file on the NE and applies it via netconfprov.
configuration: - CRFTargetList - PeeringSdpProfile configurationTargetNode: "OAM_NODE"
Auto XMLCIQ-DrivenSBC only
§ 3b-B activity › execution
YAML keyactivity.execution
TypeList of activity blocks
PositionCore activity — one block per entry
Used byMRF, DPA (Static CLI)
Manually-defined CLI execution blocks for activities that do not involve XML configuration — file transfers, file copies, permission changes, script execution. Multiple named blocks allow logical grouping of steps (e.g. transfer → load → verify).
execution: - name: "TRANSFER_FILES" description: "SFTP files to /tmp" targetNode: "MRF_NODE" method: CLI commands: - "cp /tmp/ann.tar $ANN_DIR" - "chmod 777 $ANN_DIR/ann.tar"
Static CLIMRF · DPA
§ 3c activity › postcheck
YAML keyactivity.postcheck
TypeList of activity blocks
PositionImmediately after all config/execution blocks
Used byAll node types
Verifies the configuration was applied correctly. Commands mirror the precheck — the output difference confirms what changed. Any alarms raised during the activity are captured here before the final health check.
show alarms active show crf target-list summary show peering-sdp-profile summary ls -la $ANN_DIR # MRF tail -20 phoneimporter.log # DPA
Static CLIOptional
§ 4 postNodeHealthCheck
YAML keypostNodeHealthCheck
TypeList of activity blocks
PositionAfter all activity blocks, before rollback
Used byAll node types
Repeats the same commands as the pre-health check. Confirms the node is stable and no new alarms or degraded services were introduced by the configuration. Any deviation from pre-health triggers an investigation before the MOP is marked complete.
cm_adm -a health sbc_health --test all alarm_check --action health service swms status # MRF ps -ef | grep dpa # DPA
Static CLIRequired
§ 5a rollback › precheck
YAML keyrollback.precheck
TypeList of activity blocks
PositionFirst block in rollback section
Used byAll node types
Verifies the current state of the node before starting rollback. Confirms that the records/files to be undone still exist on the NE. This prevents a failed rollback attempt caused by a partially-applied activity or prior intervention.
show status show alarms active show crf target-list summary ls -la ${ANN_DIR}.bkp_* # MRF: confirm backup exists
Static CLIRequired
§ 5b-A rollback › configuration
YAML keyrollback.configuration
TypeTable name list → auto-generated DELETE XML
PositionCore rollback — one block per CREATE table
Used bySBC (CIQ-driven)
Auto-generates NETCONF DELETE XML for every table that had CREATE rows in the CIQ data. Only primary keys are included in the payload — the NE uses them to identify and remove the records. Uses rollback xmlTemplate if defined, otherwise programmatic builder.
configuration: - CRFTargetList configurationTargetNode: "OAM_NODE" # Generates: $CREATE_ROLLBACK block with # <Record xc:operation="delete"> # <TARGET_LIST_ID>...</TARGET_LIST_ID> # </Record>
Auto XMLCIQ-DrivenSBC only
§ 5b-B rollback › execution
YAML keyrollback.execution
TypeList of activity blocks
PositionCore rollback — one block per entry
Used byMRF, DPA (Static CLI)
Manually-defined CLI rollback steps for file-based activities. Typically restores the backup file created in §2 and re-runs import/loader scripts to return the NE to its pre-activity state. Multiple named blocks allow restoring different components independently.
# MRF: restore announcement backup cp -rp ${ANN_DIR}.bkp $ANN_DIR # DPA: restore phones.dat backup and re-import cp -p OldDLUBKP/phones.dat_bkp$VER phones.dat sudo ./importtodpa.sh /export/.../startLoader.sh PHONES
Static CLIMRF · DPA
§ 5c rollback › postcheck
YAML keyrollback.postcheck
TypeList of activity blocks
PositionLast block in rollback section
Used byAll node types
Confirms the rollback completed successfully and the node has returned to its pre-activity baseline state. For CIQ-driven rollbacks, verifies the deleted records are no longer present. For file-based rollbacks, confirms the original file/version is restored and active.
show status show crf target-list summary # SBC: records gone ls -la $ANN_DIR # MRF: files restored tail -20 phoneimporter.log # DPA: old DLU version
Static CLIRequired
Part 3 — Configuration Execution Modes
⚡ CIQ-Driven XML Mode  ·  §3b-A / §5b-A
▸Reads CIQ JSON tables; rows grouped by Node and Action (CREATE / MODIFY / DELETE)
▸XML built per table via TemplateXmlBuilder (YAML templates) or NetconfSoiXmlBuilder (programmatic fallback)
▸Payload staged on NE as a file then applied via netconfprov --onerror abort
▸Rollback auto-generates DELETE XML using only primary keys from CREATE rows
▸Supported node type: SBC
activity: configuration: - CRFTargetList configurationTargetNode: "OAM_NODE" tables: CRFTargetList: xmlTemplates: create: { envelope: ..., record: ... } rollback: { envelope: ..., record: ... }
🖥 Static CLI Execution Mode  ·  §3b-B / §5b-B
▸All commands are written directly in the YAML — no CIQ data processing or XML generation
▸Multiple named blocks allow logical grouping: transfer → load → import → verify
▸File operations: SFTP, cp, chmod, tar, script execution (importtodpa.sh, startLoader.sh)
▸Rollback restores from backup created in §2 or removes newly added files
▸Supported node types: MRF, DPA (and any future file-based activity)
activity: execution: - name: "TRANSFER_FILES" description: "SFTP files to /tmp" targetNode: "MRF_NODE" method: CLI commands: - "cp /tmp/ann.tar $ANN_DIR" - "chmod 777 $ANN_DIR/ann.tar"
